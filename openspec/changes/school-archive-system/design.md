# 学校档案管理系统 - 技术设计

## Context

构建一个现代化的学校档案管理系统，支持学生和教师档案的数字化管理。系统需要支持多端访问（PC/手机），处理图片和文档的上传下载，并实现细粒度的权限控制。

**约束条件：**
- 需要支持弱网环境下的文件上传
- 单个文件最大 50MB
- 预计用户规模：500-2000 人
- 预计文件存储：50GB-200GB

## Goals / Non-Goals

**Goals:**
- 实现响应式 Web 应用，支持 PC、平板、手机三端
- 提供完整的档案 CRUD 功能
- 实现基于角色的权限控制（RBAC）
- 支持常见文档和图片格式的上传、预览、下载
- 提供管理员后台用于系统配置和审计

**Non-Goals:**
- 不开发原生移动 App（使用响应式 Web）
- 不支持视频文件上传（超出范围）
- 不实现复杂的审批工作流
- 不支持多租户（单学校部署）

## Decisions

### 1. 前端技术栈

**决策：React 18 + TypeScript + Ant Design + Vite**

**理由：**
- React 生态成熟，组件库丰富
- Ant Design 提供完整的企业级 UI 组件，响应式支持良好
- TypeScript 提供类型安全，减少运行时错误
- Vite 构建速度快，开发体验好

**备选方案：**
- Vue 3 + Element Plus：同样优秀，团队 React 经验更丰富
- Next.js：SSR 优势不明显，增加复杂度

### 2. 后端技术栈

**决策：Node.js + NestJS + TypeScript**

**理由：**
- 前后端语言统一，降低学习成本
- NestJS 提供完整的 MVC 架构、依赖注入、模块化
- TypeScript 共享类型定义
- 适合 I/O 密集型应用（文件上传下载）

**备选方案：**
- Python + FastAPI：性能略逊，生态差异大
- Java + Spring Boot：重量级，启动慢

### 3. 数据库

**决策：PostgreSQL（主库）+ Redis（缓存）**

**理由：**
- PostgreSQL 支持 JSONB，灵活存储档案扩展字段
- 性能稳定，支持全文搜索
- Redis 用于会话缓存、权限缓存、热点数据

**备选方案：**
- MySQL：JSON 支持较弱
- MongoDB：事务支持较弱，审计日志需求强

### 4. 文件存储

**决策：本地存储 + MinIO（可选 OSS 兼容）**

**理由：**
- 初期成本低，部署简单
- MinIO 提供 S3 兼容 API，未来可无缝迁移到云存储
- 支持断点续传、分片上传

**备选方案：**
- 阿里云 OSS/腾讯云 COS：成本高，依赖外部服务
- 纯本地文件系统：扩展性差，无 API

### 5. 认证方案

**决策：JWT + Refresh Token**

**理由：**
- 无状态认证，易于横向扩展
- Refresh Token 机制平衡安全性和用户体验
- 支持多端登录控制

**备选方案：**
- Session + Cookie：需要共享 session 存储，复杂度高
- OAuth 2.0：学校内部系统，不需要第三方登录

### 6. 文件上传策略

**决策：分片上传 + 断点续传**

**理由：**
- 大文件（>10MB）分片上传，提高成功率
- 网络中断后可续传，不重传已完成分片
- 前端使用 tus.js，后端使用 tus-node-server

## Risks / Trade-offs

### 风险 1：文件存储增长
- **风险**：档案文件持续增长，存储空间不足
- **缓解**：实施存储配额、定期归档旧文件、压缩冷数据

### 风险 2：并发上传压力
- **风险**：批量上传时服务器压力大
- **缓解**：上传队列限流、分片并发控制、异步处理

### 风险 3：权限配置复杂
- **风险**：RBAC 配置错误导致数据泄露
- **缓解**：权限变更审计、默认最小权限、定期权限审查

### 风险 4：移动端兼容性
- **风险**：部分老旧设备/浏览器兼容问题
- **缓解**：明确支持的浏览器版本、优雅降级、polyfill 策略

## Migration Plan

### 部署步骤

1. **环境准备**
   - 配置 PostgreSQL 数据库
   - 配置 Redis 缓存
   - 配置 MinIO/文件存储目录
   - 配置 HTTPS 证书

2. **数据库初始化**
   - 运行数据库迁移脚本
   - 创建默认角色和权限
   - 创建管理员账户

3. **应用部署**
   - 部署后端 API 服务
   - 部署前端静态资源
   - 配置 Nginx 反向代理

4. **验证测试**
   - 功能测试
   - 权限测试
   - 文件上传下载测试
   - 移动端测试

### 回滚策略

- 数据库：保留迁移前备份，提供回滚脚本
- 应用：使用 Docker 镜像版本控制，快速回退
- 文件：文件存储独立，不受应用回滚影响

## 部署规划

### 云服务器部署

- **目标**：系统将部署到云服务器（如当前服务器）
- **存储方案**：
  - 数据库：PostgreSQL 部署在云服务器
  - 文件存储：MinIO 或本地文件系统，存储在云服务器磁盘
  - 缓存：Redis 部署在云服务器
- **备份策略**：
  - 数据库定期备份
  - 文件存储定期备份到对象存储或异地

## 权限结构设计

### 角色定义

| 角色 | 说明 | 权限范围 |
|------|------|----------|
| 管理员 | 系统管理员 | 配置用户权限、系统设置、查看所有日志 |
| 领导 | 学校领导层 | 管理所有老师档案、所有学生档案 |
| 老师 | 普通教师 | 管理自己的档案 + 根据权限管理指定班级学生档案 |

### 权限模型详解

#### 1. 老师档案权限

| 角色 | 读权限 | 写权限 |
|------|--------|--------|
| 管理员 | ✅ 全部 | ✅ 全部 |
| 领导 | ✅ 全部 | ✅ 全部 |
| 老师 | ✅ 仅自己 | ✅ 仅自己 |

#### 2. 学生档案权限

| 角色 | 读权限 | 写权限 |
|------|--------|--------|
| 管理员 | ✅ 全部 | ✅ 全部（含权限配置） |
| 领导 | ✅ 全部 | ✅ 全部 |
| 老师 | ✅ 指定班级 | ✅ 指定班级 |

#### 3. 老师权限配置（管理员操作）

管理员可为老师配置学生档案的访问范围：

| 配置项 | 说明 |
|--------|------|
| 读范围 | 可查看的学生档案范围（年级/班级） |
| 写范围 | 可编辑的学生档案范围（年级/班级） |

**示例：**
- 张老师：读范围=三年级1班，写范围=三年级1班 → 可查看和编辑本班学生档案
- 李老师：读范围=三年级全部，写范围=无 → 只能查看三年级学生档案，不能编辑
- 王老师：读范围=全部，写范围=三年级1班、2班 → 可查看所有学生，只能编辑指定班级

### 操作日志

所有关键操作需记录日志，便于追溯和审计：

| 操作类型 | 记录内容 |
|----------|----------|
| 档案创建 | 操作人、时间、档案类型、档案ID |
| 档案编辑 | 操作人、时间、档案ID、修改字段、旧值、新值 |
| 档案删除 | 操作人、时间、档案ID、档案信息快照 |
| 文件上传 | 操作人、时间、文件名、文件大小、关联档案 |
| 文件删除 | 操作人、时间、文件名、关联档案 |
| 权限变更 | 操作人、时间、目标用户、变更内容 |
| 用户登录 | 用户、时间、IP、设备信息 |

**日志保留策略：** 至少保留 1 年

### 数据库设计要点

```sql
-- 用户表
users (
  id, 
  username, 
  password_hash, 
  role,  -- 'admin' | 'leader' | 'teacher'
  name,
  ...
)

-- 老师档案表
teacher_profiles (
  id,
  user_id,  -- 关联用户
  ...
)

-- 学生档案表
students (
  id,
  class_id,
  grade_id,
  ...
)

-- 老师权限配置表（学生档案访问权限）
teacher_permissions (
  id,
  user_id,           -- 老师用户ID
  permission_type,    -- 'read' | 'write'
  scope_type,         -- 'all' | 'grade' | 'class'
  scope_value         -- 年级ID/班级ID，null 表示全部
)

-- 操作日志表
audit_logs (
  id,
  user_id,           -- 操作人
  action,            -- 操作类型
  resource_type,     -- 资源类型：'teacher_profile' | 'student' | 'file' | 'permission'
  resource_id,       -- 资源ID
  old_value,         -- 旧值（JSON）
  new_value,         -- 新值（JSON）
  ip_address,
  user_agent,
  created_at
)
```

### 权限检查流程

1. 用户请求访问档案数据
2. 系统判断档案类型（老师档案 / 学生档案）
3. 根据用户角色检查权限：
   - **老师档案**：管理员/领导可访问全部，老师只能访问自己
   - **学生档案**：管理员/领导可访问全部，老师检查权限配置表
4. 记录操作日志
5. 返回结果或拒绝访问
